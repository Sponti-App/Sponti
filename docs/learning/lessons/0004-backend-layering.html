Lesson 4 · Crossing into the backend

Backend layering

Your win: follow the same join from Lesson 2 past the network boundary and through api/'s four layers — and learn the one rule that tells you which file a given piece of logic belongs in.

In Lesson 2 the join ended at PATCH /events/:id/me. That's the network boundary. On the other side, api/ is laid out in four layers that mirror the request's life: route → controller → service → model. Every endpoint follows the same shape, so once you can read one, you can read all of them.

The four layers

  1. RouteMaps a URL + method to a handler and stacks middleware: auth, then validation. routes/eventRoutes.ts
  2. ControllerThin. Pulls inputs off the request, calls the service, shapes the HTTP response. No business logic. controllers/eventController.ts
  3. ServiceWhere the actual logic lives — the RSVP rules, notifications, transactions. services/eventService.ts
  4. ModelThe Mongoose schema — the shape persisted to MongoDB. models/EventMember.ts

The trace, continued from Lesson 2

The frontend sent PATCH /events/:id/me with { rsvpStatus, memberWillArriveAt }. Here's its life inside api/:

routerouter.use(requireAuth) then validateRequest({ params, body }) → controller
↓  (rejected here if the token or body is bad — logic never runs)
controllerupdateMyEventMembership: getAuthenticatedUserId(req) + route param + req.body → service
↓
serviceupdateMyRsvp: load membership, set status/ETA, save, fire RSVP notification
↓
modelEventMember doc .save() → MongoDB
↑  controller wraps the result as res.json({ data })

The rule: thin controllers, fat services

Look at any controller method — they're almost identical and almost empty: grab inputs, call one service function, return { data }. That emptiness is the design. All decisions live in the service, which means:

  • Logic is testable without HTTP — and indeed eventService.test.ts exists, the controllers don't need tests.
  • Validation is done before the controller (the validateRequest middleware + a Zod schema), so the service can trust its inputs.
  • The same envelope — { data } — comes back every time, which is why the frontend's apiFetch can blindly unwrap .data.

So when you ask "where does X belong?": a URL/permission concern → route; pulling request fields or shaping the response → controller; an actual rule or side-effect → service; the stored shape → model.

Gap-spotting instinct: if you ever find business logic in a controller (an if deciding something, a DB query), that's a smell — it belongs one layer down. The privacy-enforcement bug (issue #88) is the mirror image: a rule that should be in the service/query but is missing entirely.
