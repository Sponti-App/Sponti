Lesson 3 · The other kind of component

The create path

Your win: recognise the second component archetype — the "smart" self-contained feature — and see the adapter layer that lets it talk to the backend. Plus: spot exactly where the hide-able "fluff" lives.

Lesson 2's event-detail-sheet was dumb: no state, no API calls, just props and callbacks. new-event-drawer.tsx is its opposite — ~1,900 lines that own a whole form and call the backend themselves. Both are correct. Knowing which kind you're looking at is half of reading a React file fast.

Dumb / presentational Lesson 2

event-detail-sheet

  • Props in, callbacks out
  • Only UI state
  • Parent owns the wiring
  • Reused in many places

Smart / feature Lesson 3

new-event-drawer

  • Owns its form state
  • Calls the API itself
  • Self-contained feature
  • Rendered once, globally

1 · One drawer, opened from anywhere

The drawer is mounted once by NewEventDrawerProvider (remember it from the Lesson 1 provider stack). Anything can open it via context:

FABbottom-nav.tsx → useNewEventDrawer().openDrawer()
URL/event/new → just calls openDrawer() over the home map (page stays behind it)

That's a neat trick: visiting /event/new directly doesn't render a separate page — it opens the same drawer on top of the map, so creation always feels lightweight. One create UI, two doors.

2 · The trace: form → backend

Fill the form, hit create. handleSubmit (new-event-drawer.tsx:866) runs:

statelocal form state: title, type, time range, location, audience, invite toggles…
↓  build a DraftEvent
adapterevents.adapter.ts — createEventRequestFromDraft(draft, audience, timeRange)
↓  UI shape → API contract
lib/apievents.ts — createEvent(body) → apiFetch POST /events
↓
backendeventRoutes — POST / → validateRequest(createEventBodySchema) → controller → service

3 · Why the adapter exists

The drawer thinks in UI terms (a "DraftEvent": chips, toggles, friendly labels). The backend thinks in contract terms (a "CreateEventRequest": startAt, visibility, allowGuestInvites, GeoJSON location). The adapter is the translator between them:

The adapters keep UI/prototype shapes separate from backend API contracts… this lets the form stay focused on UI state while the API module owns naming, defaults, invite modes, and payload structure. — spa/lib/api/events/EVENTS_WIRING.md

This is why the form can be restyled without touching the API, and the API contract can change with edits confined to one adapter function. Same separation principle as Lesson 2 — just expressed as a data boundary instead of a callback boundary.

4 · Where the hide-able fluff lives

This component is exactly where the roadmap's "hide, don't delete" work happens. Inside the drawer's form state:

Roadmap targets: allowForward (re-share toggle — frontend-only, never sent to the backend) and the +1 / guest-invite controls (backend-wired but no redemption UX). When you build feature-flags.ts, these are the first fields you'll gate off — right here in new-event-drawer.tsx. Custom circles, also wired in this form, stays on.
